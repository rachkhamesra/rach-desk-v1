# Desk

A searchable stock screen on GitHub Pages, rebuilt every weekday evening from NSE and BSE end-of-day files.

Main screen: search a ticker, see its adjusted price as candlesticks (adjusted open, high, low and close) with moving averages, delivered-share bars (green = up on above-average delivery, red = down on above-average delivery, faded green/red = ordinary days, grey = a move under 0.5 standard deviations), its relative strength against the Nifty, and the futures open-interest build-up. Other tabs combine delivery, relative strength and moving-average proximity into one Signal Confluence view, track cash accumulation and conference calls, and monitor BSE and MCX options-premium turnover.

## Set up (once)
1. Create a GitHub repo and push this folder.
2. Settings, Pages, Source: **GitHub Actions**.
3. Actions tab, run **Daily desk** once ("Run workflow"). The first run downloads about 14 months of files (a few minutes). After that it runs by itself.

The bundled F&O conference-call summaries work without an API key. A future automated refresh can be enabled by adding an OpenAI API key at **Settings → Secrets and variables → Actions → New repository secret** with the name `OPENAI_API_KEY`; the current prototype does not require it.

The page is at `https://<you>.github.io/<repo>/`. Locally: `pip install -r requirements.txt`, then `python run.py` (writes `site/index.html`). `--asof 2026-10-23` rebuilds for an earlier date; `--days 1100` pulls about three years.

## What happens automatically
A small Cloudflare Worker in `scheduler/` is the primary clock: GitHub's own `schedule:` trigger is best-effort and has started jobs hours late or not at all. The Worker starts the **Daily desk** workflow through the API every day at 06:00, 06:30 and 07:00 IST (until a build has run that day, or MCX or the newest session has something new), on weekday evenings every 30 minutes from 19:00 to 22:00 IST (only when the newest NSE/BSE session, with its BSE delivery, or MCX has something new), and on Saturday and Sunday at 20:00 IST as a backup. See `scheduler/README.md` to set it up. The workflow's own crons remain as a backstop and skip in seconds when a build has already covered them. A run restores the small cached history (about 77 MB) and asks NSE and BSE for every trading day it does not yet have (one day of files on a normal evening). Manual runs build unless you choose another mode. City temperatures are downloaded at most once a week per city (they trail real time by about five days anyway), and a build spends at most a few minutes on temperature and power downloads. The user's computer does not need to be on.
- If the newest NSE/BSE files are not out yet, the run immediately keeps the last complete market session rather than publishing partial data. The later scheduled run checks again automatically.
- On an exchange holiday NSE serves the previous day's file; the job notices and rebuilds on the last real session.
- GitHub can start scheduled jobs a few minutes late. In a public repo GitHub switches scheduled workflows off after 60 days without any repository activity; re-enable them in the Actions tab, or keep the repo private.
- NSE and BSE sometimes block GitHub's servers. If the run fails on downloads, run `python run.py` from cron on your own machine and push `site/` to a `gh-pages` branch; nothing else changes.

## Conference-call intelligence
The repository bundles the latest researched transcript analysis directly in `call_intelligence_seed.json`, so it renders as ordinary website text without a model call at build time. The current [Transcript Intelligence Research Snapshot](TRANSCRIPT_INTELLIGENCE_README.md) contains exactly Eternal, Shriram Finance, Infosys, Punjab National Bank, PG Electroplast and Indian Hotels, provided each has a verified exchange-served transcript. Cached call data is filtered to this publication scope.

Every published fact and evidence passage comes from the latest qualifying NSE/BSE transcript. Guidance changes are shown only when management explicitly states an increase, improvement, reduction, downgrade or upgrade in that same transcript. Old → new figures appear only when both figures are stated there. The main stock tab places the most material validated change in a green or red row above the chart and opens the contextual Call Intelligence evidence; the row stays hidden when no change qualifies.

The STOCKS page shows the result below the charts: next-quarter outlook, the subjects receiving the most analyst questions, a congratulations index, short supporting excerpts, and sector-specific metrics. Manufacturers focus on revenue and volume growth, order inflow, demand, margin outlook and EBITDA margin. Banks and lenders focus on credit growth, credit–deposit ratio, disbursements, NIM, asset quality and credit costs. These are model-generated reading aids; the linked exchange transcript remains the source of record.

## Alternative data (experimental)
The amber **Alternative Data** tab reads whether the season is running hotter or cooler than before, as a pointer to demand for ACs, coolers, fans, heaters and geysers. `heat.py` pulls daily mean and maximum temperature for the 25 cities in `config/cities.json` (edit that file to add or change a city; regions are North, East, West and South, with central India under West) from the Open-Meteo archive (ERA5 reanalysis) and the Niño 3.4 index from NOAA. The first run downloads 1991 onward for each city and takes several minutes; after that a run refreshes the last 40 days once a day. Cached data lives in `data/heat/`, and a city that fails to download keeps its last good data.

What it shows, all against the same days of earlier years and the 1991–2020 normal (a 15-day smoothed daily average): region cards (year to date, last 30 days, versus the previous two years and the share of warmer days); cooling-season (March to June) and heating-season (December to February) tables for each region against the previous season, with a "tailwind or headwind" read; six large cities (Delhi, Mumbai, Bengaluru, Hyderabad, Chennai, Kolkata) always shown as a 3-by-2 grid of year-versus-year charts (14 or 30-day trailing mean of the daily mean or maximum, Feb 29 removed); and an 18-month heat grid of all 25 cities. Regions are simple averages of their cities. Values are ERA5 grid-cell estimates, not station readings, about a week old, and temperature is one input to demand, not a forecast. Open-Meteo's free tier is for non-commercial use.

### Power generation (second view of Alternative Data)
`power.py` and the `nppdgr/` package read the CEA Daily Generation Report, sub-report 2 (station and unit level generation, coal stock days, outages) from npp.gov.in. Each file is parsed, checked against the file's own region totals (a mismatch fails that day and is recorded), then reduced to two small tables in `data/power/`: `fleet.csv` (by region, sector and fuel) and `owner.csv` (by plant owner). Files appear one to two days late; the newest 6 days are downloaded again every run because the portal revises them, and gaps in the last 12 days are retried. Wind and solar are not in this report, so totals are conventional generation, not national supply. Layouts before Nov 2019 are not supported; history starts at 1 Jan 2023 (`FIRST_DAY` in `power.py`). The first build downloads history newest-first within a time budget (`POWER_BUDGET_S`, 900 seconds by default) and carries on at the next build.

The view is about companies, not regions or states: three year-versus-year charts in one row (all conventional, coal and lignite, hydro), a company chart below them with a selector (NTPC, Adani Power, Tata Power and the other matched owners, all fuels together), a shared 14 or 30-day trailing-mean control, and a table of companies over the last 30 days (capacity, generation, change against the same weekdays a year earlier, coal plant load factor and coal stock days). State-owned and imported generation, unmatched plants and plants marked `REVIEW` are left out of the company table and the view states what share of generation that is. Plant-to-owner matching is hand-maintained in `config/plant_owner.csv` (edit that file, not the code). A coal stock of 0 may mean "not reported", so it is left out of the averages.

Under the company chart, two bar charts total the selected company's generation by calendar month (last 24 months) and by Indian fiscal quarter (Q1 is April to June, last 12 quarters). A month's total is its observed daily mean times its calendar days, so a missing day or Feb 29 cannot skew it. The month or quarter in progress is drawn in orange: solid for generation so far, dashed for an estimate that assumes the remaining days run at the average of the last 14 or 30 days (the smoothing control), and a white tick marks the same period a year earlier. The estimate is a straight run-rate; it ignores seasonality, outages and holidays, so treat it as a pace check, not a forecast.

**IEX day-ahead price (merchant power price).** `iex.py` reads the daily table on IEX's Market Snapshot page (`iexindia.com/market-data/day-ahead-market/market-snapshot`, any range of up to 31 days from April 2022): purchase and sell bids, cleared volume (MCV), and the simple and volume-weighted market clearing price (MCP), stored in `data/power/iex_dam.csv`. It is an HTML table, not an API, so a layout change makes the parse return nothing and the last good data stays. The power view shows two year-versus-year charts (weighted price in Rs per kWh, cleared volume in MU a day) with the same 14 or 30-day smoothing, and a line with the latest day. The first run fetches month by month from 2023 within a 150-second budget (about 47 requests); after that the two newest months are fetched once a day. If IEX refuses automated requests from GitHub's servers the section simply does not appear, and the build log says `iex:` with the reason.

## Management outlook (six labels)
`outlook.py` turns the tagged next-quarter points of a call into one of six labels, shown as a row above the stock chart (and as a Watchlist column): **bullish, optimistic, positive, muted, cautious, bearish**. Each point's tone is scored (positive +1, neutral 0, cautious −0.75, negative −1.5) and averaged; an explicit guidance raise or cut adds or subtracts 0.25 each (capped at ±0.5). Score ≥ 0.9 with strong language ("accelerating", "record", "raised"...) or a guidance raise is bullish (≥ 0.75 needs three strong points or two raises); ≥ 0.5 optimistic; ≥ 0.25 positive; down to −0.1 muted (no clear direction); down to −0.55 cautious; below that bearish, but only if at least one point is explicitly negative. Fewer than three points gives no label. It is a reading aid built from those tags, not an independent view; open the transcript before relying on it. It needs no model call, so new transcript batches are labelled automatically.

## Exchange Trackers
The BSE tracker stores daily Options Premium Turnover in ₹ crore from January 2025 onward. It first reads BSE Equity Derivatives Key Statistics and, when that endpoint rejects a cloud runner, derives the identical options-premium value from BSE's official daily UDiFF derivatives file. The page plots the five-session rolling premium turnover against BSE Ltd's adjusted share price, compares the newest observation with all prior occurrences of the same weekday in the year, shows monthly average daily premium turnover, and writes a short factual summary from those calculations.

The Exchange Tracker has BSE and MCX sub-tabs. The MCX tracker starts with the official date-wise OPTFUT Premium Value reports supplied through 28 October 2026 and retains FUTCOM Total Value for later use. It compares the current part of the month with the same bucket in prior months: Week 1 = days 1–8, Week 2 = 9–16, Week 3 = 17–24 and Week 4 = 25–month-end. It attempts an incremental refresh from MCX Historical Data, retains the last verified report if MCX blocks automated retrieval, and labels that state visibly rather than presenting stale data as current. Its Daily Read also retrieves upcoming MCX options expiries from Groww's public commodity calendar.

## Password lock (off by default)
`lock.py` can replace `site/index.html` with an unlock screen holding the encrypted page (gzip, AES-256-GCM, key from PBKDF2-HMAC-SHA256 with 600,000 rounds, decrypted in the browser with WebCrypto). The workflow runs it only when the repository variable `SITE_LOCK` is set to `on` (Settings, Secrets and variables, Actions, Variables), and then it needs the `SITE_PASSWORD` secret (12+ characters) and fails the deploy rather than publishing an unlocked page. With the variable unset or anything else, the site is published as a plain page, including `site/corporate_actions.csv`. It keeps casual visitors out, but the encrypted file is still public and the repository is not hidden by it. Changing the password locks out remembered devices until they enter the new one. Locally, `SITE_PASSWORD=... python lock.py site/index.html` locks a built page. Needs a current browser over https (or localhost).

## Base follow-through
It is the Follow-Through view of the Breakout Bases tab, and uses that tab's filter buttons.
`metrics.base_followthrough` replays the Breakout Bases scan on every past session in the loaded history and records what happened after each signal. A signal is the first day a stock reaches a stage (building, near, fresh) after at least 10 sessions out of it. Returns are measured from that day's close at 5, 10 and 20 sessions, with the excess over the Nifty, the worst dip, and whether the low undercut the base support within 20 sessions. Only data up to the signal day feeds the signal. The tab recomputes win rate, average and median from the signals using the same five filters as the Breakout Bases tab. With the default 420 days of history the sample is small (about 190 replayed sessions); run with `--days 1100` for three years. Results are historical and say nothing certain about the next trade.

## Corporate actions (automatic)
NSE and BSE do not adjust the previous close, so a split or bonus looks like a crash. A one-day jump is treated as a corporate action when
1. it is confirmed by an exchange signal: the ISIN changed, or the futures lot size moved the opposite way; or
2. it has no such signal (the stock was not in F&O then) but rupee turnover stayed normal. A split changes the share count, not the rupees traded; a crash or news gap comes with a turnover spike (3x the prior 20-day average or more).

Otherwise it is a real move and is left alone. Prices before the date are multiplied by the factor and delivered shares and open interest divided by it, so charts, averages and the 20-day baseline stay on one share basis. Each adjustment shows as a green dashed line on the stock's chart, and `site/corporate_actions.csv` is an audit log. On the 14 events in the first year: 13 adjusted (KOTAKBANK 5:1 split, LICI and PIDILITIND bonuses, ANGELONE 10:1, the VEDL demerger, among them) and POLICYBZR's -36% crash left alone. Nothing needs maintaining by hand; `corp_actions.csv` exists only as an override if you ever disagree with a call (symbol,date,action,ratio,note).

## Results calendar and pre-result activity
Each build asks NSE's board-meetings feed for every meeting from a week back to 120 days ahead (without a date range NSE returns only its latest 20, so the range is essential) and keeps the ones that consider financial results. A re-announced date replaces the older one. The workflow runs three times a day, so new intimations appear within hours. The feeds are cached and merged, so temporary NSE downtime leaves the last known dates in place. NSE's feed covers every NSE-listed stock in the universe; BSE's own calendar API refuses automated requests from cloud servers, so BSE is not read separately.

Where it shows:
- **Call Library, Upcoming Results:** every announced result meeting in the universe, with filters for Top 500 by market cap, F&O, five market-cap bands (market caps are NSE's last half-yearly average, so a size band, not a live value), date window (today, 3, 7, 14 days) and a ticker or company search.
- **Stocks chart:** a "Result in N days" banner above the chart with the date, meeting type, period and the NSE filing, and a dated badge beside the stock name.

For each result the scan examines the three completed trading sessions before the declaration date. `PRE-RESULT ACTIVITY` means that, on at least one of those sessions, delivered shares were above the prior 20-session average and the absolute price move was greater than 0.8 times the stock's prior-60-session daily-return standard deviation. Both baselines are shifted, so the signal uses no future data.

## Definitions
- Delivered shares = NSE + BSE (mapped through the ISIN). Delivery % is shown for reference, never used to rank.
- 20-day average = mean of the previous 20 sessions' delivered shares; ratio = today / average.
- "Above-average delivery" on the chart is a selector (1.0x, 1.25x default, 1.5x, 2.0x). "Under 0.5 standard deviations" = |daily move| below half the stock's prior-60-session standard deviation.
- OI build-up: price up and OI up = long build-up; price down and OI up = short build-up; price up and OI down = short covering; price down and OI down = long unwinding.
- Relative strength: stock / Nifty, rebased to 100 at the start of the range, with its 50-day average. Relative performance = (1 + stock) / (1 + Nifty) - 1.
- Persistent delivery: at least 3 of the last 5 sessions at 1.25x or more. At a moving average: within 0.5 sigma of the average (sigma = 60-session daily standard deviation).
- Moving averages 32, 50, 100, 200, 233, 377, 610; each switches on when there are enough sessions. Percentile columns read 1Y until about three years of history exist.

## Backtest panels (very experimental)
Four small panels at the bottom of Alternative Data, Power generation: what works, what held in more than one year, what doesn't, and whether there is a threshold. The question is whether generation or IEX day-ahead price moves have ever predicted the share price of NTPC, Adani Power, Adani Green, NHPC and JSW Energy.

**It is run on a local machine, not in the daily build.** From the repo root, with the power data in `data/power`:

```bash
python backtest.py
```

That downloads share prices (Yahoo Finance's unofficial API, cached in `data/backtest/`), scores everything, and writes `config/backtest_results.json`, which you commit. The build only reads that file, so a blocked or changed price source can never break the site. Re-run it when you want fresher results.

- **Signals:** generation 30-day average vs a year earlier; generation 14-day vs 60-day; the same two for IEX weighted price; and "both rising". Generation is lagged 2 days and price 1 day, as they would be published.
- **Scoring:** every 5th trading day, the forward 10- and 20-day return minus Nifty, scored per calendar year (2024, 2025, 2026). Verdicts: works, sometimes works, could work, doesn't work, inverse.
- **Threshold panel:** each signal is turned into standard deviations from its own past year and pooled over the five stocks. The bars show the average 20-day excess return by band; a cut-off only counts if the gap is more than about two standard errors.
- **NHPC** uses all-India hydro generation as a stand-in. **Adani Green** has no generation data (wind and solar are not in the CEA report), so only its price tests run.
- A screen for ideas: about a dozen independent observations per test per year, no costs, hand-matched ownership.

## Short ideas tab (experimental)
F&O stocks only, from `shorts.py`. Six yes/no screens on the existing price, delivery and open-interest data: cash selling (down day, below the 50 and 100-day averages, delivery above its 20-session average), laggards (behind Nifty by 5 points over 20 days and 10 over 3 months, below the 50-day), breakdown below the prior 40-day low on delivery, rejected at the 50-day average, short build-up (down 3% in three sessions with OI up 5%), and near the 52-week low while lagging. The overview lists stocks flagged by two or more screens.

Each screen carries a **replay**: the same rule applied to every held session, then the stock's move against Nifty over the next 10 sessions (one flag per stock per 10 sessions), shown next to the average F&O stock. On the current history (about 280 sessions) none of the screens shows an edge over that baseline, and the page says so. Treat the lists as things to look at, not signals.

Every Short Ideas subtab also draws a chart per flagged stock (up to 30): close, 50 and 100-day averages, with only the last 10 sessions on which that screen's rule was true shaded and dotted (older firings are not shown). The overview charts stocks hit by two or more screens, with each screen in its own colour.

The Short Ideas charts are candlesticks over delivered-share bars (coloured by the day's move, brighter when delivery is at least 1.25x its 20-session average, dashed 20-day average), as on the Stocks screen. **Support and resistance (experimental)** are price-congestion zones: each of the last 250 sessions spreads its delivered shares over its high-low range, and peaks in that profile are where the most shares changed hands. Zones at most 3% either side of a peak, at least 6% apart, up to two on each side of the current price, drawn as green (below) and red (above) bands and listed on each card with their distance. They are a description of where holders are anchored, not a forecast; a zone that has been broken stops mattering.

## Splits and bonuses: the exchange feed
Price-only detection (`corp.py`) can miss a bonus or split that comes without an ISIN or lot-size change, as happened to City Union Bank's 1:3 bonus (ex 12 Jun 2026): the day's ratio of 0.7855 sat just past the cut-off and bonus-news trading made turnover look like a spike, so the chart showed a 21% crash. `corp_feed.py` now reads NSE's corporate-actions feed (`/api/corporates-corporateActions`), turns "Bonus a:b" and face-value splits into price factors (a split and a bonus with the same ex-date multiply), and caches them in `data/corp_feed.csv`. A feed row is applied only on the session where the price actually moved by about the announced ratio, so a stale or mismatched row cannot invent an adjustment, and it replaces any price-estimated factor for the same event (Adani Power's 1:5 split moves from an estimated 0.25 to the exact 0.2). If the feed cannot be fetched the cached copy is used and detection falls back to prices alone. `corp_actions.csv` hand overrides still take precedence.

## Technical Patterns tab (experimental)
Three subtabs, each with a status filter, an F&O-only toggle, a table and a candlestick chart per stock (trendlines, the swing points they run through, and a measured-move target): **ascending triangle**, **descending triangle** and **rectangle**. `patterns.py` scans the top-1,000 shares that trade at least ₹2 crore a day, on daily adjusted prices, and the rules are written out on the page under "How this pattern is defined". In short: swing highs and lows (the best of four sessions either side) are clustered into a flat level (three or more touches within 2%, 12 or more sessions apart: touched more than twice); the sloped side is the chain of rising lows (falling highs) joined first to last, at least three points, moving at least 3%; a triangle starts 6% to 50% of price tall and has narrowed to 80% or less; a rectangle needs three or more touches each side within 2%, seven in all, a 7% to 40% range with 90% of closes inside and no drift of more than half the range. A break counts as fresh for ten sessions (BREAKOUT/BREAKDOWN), SETUP is within 4% of the trigger and FORMING within 10%. Target = the break level plus or minus the widest height.

**Calibration, honestly:** on 100 simulated random price paths the same rules flag some pattern in 38; on the real top-1,000 about 18% of stocks show one. So a pattern on its own is weak evidence, and the replay/back-test that Short Ideas has is not built here yet. Both of the reference charts (Motilal Oswal's ascending triangle, Supreme Industries' descending one) are picked up by the rules.

## Two years of history, and how it fills in
The build now keeps about two years of NSE bhavcopy sessions (`--days 760`, about 510 sessions) instead of fourteen months. Longer history comes in gradually so no single run has to fetch it all: `--backfill 150` fetches at most 150 weekdays older than the oldest session already held, newest first, so the history stays contiguous and a fresh cache fills in over a couple of daily runs (the page uses whatever has arrived). Downloads that return an HTML error page with a 200 status are rejected. The delivery ratio and each day's direction are no longer sent to the page: it rebuilds them from the closes and delivered shares with the same rules (checked identical to the server's on real data), and stocks without futures send no open-interest array. That keeps the page at about 28 MB despite the longer history.

## Weekly patterns and flags on the stock page
Every Technical Patterns subtab has a DAILY | WEEKLY switch. The weekly scan runs the same rules on weekly candles (open of the first session, highest high, lowest low, close of the last session, delivered shares summed; the week in progress is the last candle). Only bar counts change: a swing beats 2 weeks either side, a flat level's touches are 5+ weeks apart, a pattern is 26 to 156 weeks old, a break stays fresh for 4 weeks; every percentage rule is the same. Weekly charts use 10 and 30-week averages.

**The stock page lists every screen that flags the stock** in a "Flagged in" row above the chart: daily and weekly patterns (with status), the Short Ideas screens, Cash Accumulation (confirmed or tracking), Breakout Bases and 52-week highs. Each chip jumps to that screen. Each detected pattern gets its own small chart in the side panel (**Chart patterns**), drawn in the browser from the stock's own prices on the timeframe it was found on (weekly patterns get weekly candles): the two lines with the shape shaded, the swing points they run through, the day of the break and the measured-move target, with the pattern's numbers underneath. The main price chart is left clean. The chart gets a 2Y range button.

## Cleaner tabs, "new" markers, replay and score
**Technical Patterns now holds Breakout Bases and Short Ideas** as subtabs next to the three patterns, so the top row is Stocks, 52W Highs, Technical Patterns, Cash Accumulation, Call Library, Exchange Tracker, Peer Radar and Alternative Data. The stock page's "Flagged in" chips still jump to the right place, including the nested Short Ideas screens.

**Since the previous session.** The pattern scan is rerun on the data as it stood one session earlier and compared. A pattern the stock did not have then is marked NEW; one that had not yet broken and now has is marked JUST BROKE OUT/DOWN. A digest card at the top of the tab counts these (with new Short Ideas, new Cash Accumulation and fresh breakout bases) and lists the stocks; a line underneath shows the new flags on **your watchlist** (read from this browser). Each table has a "NEW / JUST BROKE" filter.

**Score, 0 to 5**, orders each list within its status: a fresh break (2) or a setup near the trigger (1), delivery at least 1.25x its 20-session average (1), 3-month relative strength leaning the pattern's way (1), the other timeframe showing a pattern with the same lean (1). It is a way of ordering, not a probability.

**Replay** (`python pattern_replay.py`, run locally, results in `config/pattern_replay.json`): the same detectors run on every fifth session (every week for weekly) over the history held, recording each fresh break once at the moment it would have been visible and measuring the move against Nifty about one, two and three months later (20, 40 and 60 sessions; a break counts for a horizon only if it has that much history after it), as an average and a median, next to the average liquid stock sampled the same way. **High delivery means delivered shares on the break session itself at least 1.25x their own recent average** (20 sessions for daily, 10 weeks for weekly), and the tables lead with those breaks: the Technical Patterns tables default to them, the replay tables put them first, and the digest and the stock page flag them. The average stock's median is about -0.6% against Nifty at every horizon (a few big winners lift its average), so compare medians.

First full run (about 515 sessions, 3,300 breaks), high-delivery breaks: daily ascending-triangle breakouts show no edge at any horizon (+0.5% / median -0.6% at 20 sessions, 49% up at 60); daily rectangle breakouts do better with delivery than without (+4.1% / median +3.4% and 62% up at 60 sessions, against +2.7% / +2.3% and 58% for all of them); weekly ascending breakouts +2.9% / +2.3% at 40 sessions and +4.2% / +6.4% at 60, 56 to 61% up. Breakdowns on high delivery fall further than the rest for about a month (weekly descending breakdowns -2.9% / median -2.4% and 62% down at 20 sessions against -0.9% / -0.7% and 55% for all of them) and then rebound: by 60 sessions they have not worked. Samples run from about 10 to a few hundred overlapping events from one market regime, with no costs, so read these as suggestive, not proven; the weekly rectangle rows (10 to 16 high-delivery breaks) are too few to read.

## Trade-for-trade stocks keep their history
A stock moved by the exchange into the trade-for-trade segment (series BE, or BZ) used to vanish from the price history for as long as it stayed there, because only the EQ series was read: Prime Focus lost 44 sessions between May and July 2026 and its chart showed a hole. The loader now keeps EQ, BE and BZ rows (never the BL block-deal rows or SME boards), EQ winning if a symbol appears in two. No intraday trading is allowed in BE or BZ, so the whole traded volume is taken as delivered volume (the delivery file prints "-" for them). Because the parser changed, every cached day has to be parsed again: `data/parsed.version` records the parser version and a mismatch discards `parsed.pkl`, which makes the next build (a full run in CI, about 10 minutes of downloads plus parsing) rebuild from the raw files.

## Renamed stocks and untraded sessions
**Renames are stitched.** When the exchange renames a symbol the ISIN stays the same (Zomato became Eternal on 9 Apr 2025, Tata Motors became TMPV, LTIM became LTM, GMR Infra became GMR Airports, and about a hundred others), and the new symbol used to start a short life on the rename day, so the stock looked as if it had no history before it. `nse.symbol_aliases` finds every ISIN traded under several symbols that never overlapped in time and maps each earlier symbol to the latest; `nse.canonical` applies that to prices, delivery and futures when the parsed days are read (the cached frames are untouched), and the corporate-action feed and `corp_actions.csv` rows are mapped the same way. An ISIN under two symbols on the same day is left alone, since that is two instruments. Stitching also exposed real events that the short histories had hidden, such as Acutaas' 1:1 bonus and the Tata Motors demerger.

**Untraded sessions carry the last price.** A stock missing from the exchange's file on a day did not trade. `metrics.carry_last_trade` fills those sessions with the last traded price whatever the length of the gap (before, only five), draws them as flat candles with no delivery, and never carries a price past a stock's last real trade, so a delisted stock does not run on. An audit of the 1,017 tracked stocks found 9 with such gaps (Ujaas, Swan Defence, BCG, Reliance Infra and a few others); none of the missing days appears in the file under any other series, so there is nothing more to recover for them. After the fixes none of the 999 stocks on the page has a hole inside its price history.

## Build speed
Measured on the full data: the pattern scans went from about 100 seconds to 12 and the breakout-base follow-through replay from 36 seconds to 0.3 on a normal day. `patterns.swings` and `patterns.clusters` are vectorised (identical output to the plain loops they replaced: checked on all 1,998 stock-timeframe scans of the real data, 221 patterns, 0 differences, and by tests on noisy data with gaps and ties), and the rectangle detector no longer recomputes the swing lows for every top. The base-signal replay is incremental: `data/base_events.pkl` keeps the signals found at each session, and a build scans only the sessions added since, provided a fingerprint of all earlier prices and delivery is unchanged and the symbol list is the same (a split that restates history, or a new F&O stock, rescans everything); what happened after each signal is always recomputed. Checked identical to the original function on real data (4,526 signals, 21 columns). The cache file is in the workflow's cache lists.

## Page load: lazy panels and lazy stock data
Measured in headless Chromium with the CPU slowed 4x (roughly a mid-range phone): load time fell from 4.7 s to 2.3 s, JS heap from 58 MB to 22 MB, DOM nodes from 128,000 to 8,600 and script time from 1.66 s to 0.44 s. The download is unchanged (the page is 27 MB, about 8.9 MB compressed in transit): the saving is in what the browser does afterwards.
- **Per-stock data on demand.** Each stock's close, open/high/low, delivered shares and open-interest arrays arrive as one string (`S.a`) and are parsed only when the stock is first opened (`ensureStock`); the page no longer parses 17 MB of numbers or rebuilds the delivery ratio and direction for 999 stocks at start. The stock list and watchlist use the summary (`sm`, which now carries the last price).
- **Heavy tabs on demand.** The Technical Patterns (with Breakout Bases and Short Ideas), Call Library, 52W Highs and Exchange Tracker panels are held as inert text (`<script type="text/plain" id="lazy-...">`) and turned into DOM the first time their tab is opened (`ensurePanel`); their click handlers are bound then, to that panel only (`bindPanel(root)`). Opening Technical Patterns the first time takes about 1.6 s at 4x slowdown, after which it is instant. `lazy_panel` escapes `</script` and `<!--` so nothing in a panel can break the container; a test checks the round trip.
- **A browser check.** `tests/browser/check.js` (needs Playwright) drives every lazily loaded tab, the stock chart, the watchlist and the jump links and writes what it saw to JSON; running it before and after a change to the page and comparing the files shows any change in behaviour. This change was verified that way: 41 observations, identical apart from one count that moved only because the rolling two-year window dropped its oldest session that day.

## Today tab
The page opens on **Today**, laid out as a landing page: a headline and six tiles (Nifty today, high-delivery breakouts and breakdowns, new Short Ideas, new Cash Accumulation, fresh bases); **three charts worth a look** (the best high-delivery breakout, the best breakdown, drawn with the pattern chart, and the strongest short idea, with a sentence on each); **activity across exchanges and power** (BSE and MCX options premium turnover and power generation, each with a sparkline and its direction against five sessions ago, or against last year for power, plus one line saying which are running hotter or cooler); **short ideas** (stocks flagged by two or more screens); **one call** (the newest analysed call: the first next-quarter point with its speaker, what analysts pressed on, a key risk); and **also new today** (more breaks, cash accumulation, fresh bases, and your watchlist's new flags). Every block links to its full tab, a stock link opens its chart, and a `#TICKER` address still opens straight on that chart. The breakouts and breakdowns are ordered by whether they came on the latest session, then by conviction and delivery.

## Three years of history, and which touches count
- **History is now about three years** (`--days 1100`, about 710 sessions), so a pattern whose first test of a level is more than two years old is still seen (MOTILALOFS's flat top began in late 2024). The extra year arrives gradually, `--backfill 150` weekdays per run, and the page uses whatever has arrived. The page grows to about 34 MB (about 11 MB compressed). The corporate-action feed now fetches the older ex-dates once when the history is extended backwards (`data/corp_feed.from` records how far back it has read; it is in the cache lists); without that, a split inside the new years (MOTILALOFS's 3:1 bonus on 10 Jun 2024) shows as a crash. One BSE delivery file (25 Apr 2024) spells a column with a backtick; the reader now accepts it.
- **Touches of a flat level must be a gap apart.** Swing highs a few bars apart are one test of the level, not two (12 sessions on the daily scan, 5 weeks on the weekly).
- **Two touches are enough when they are far apart.** A flat level whose first and last touch are at least 60 sessions (12 weeks) apart needs only two touches instead of three (`Cfg.wide`). It applies to triangles; rectangles still need three on each side.

## Short Ideas: 200DMA retest
A seventh screen: a stock that **closed under its 200-day average on delivery at least 1.25x its own 20-session average, fell at least 4% under the average afterwards, and has now come back to within 3% under it (or 1% over)**. It stops counting once the stock closes more than 3% back over the average, and 60 sessions after the break. Unlike the other screens it covers every liquid share (₹2 crore a day, about 950 names), not only F&O, so its subtab has an **ALL LIQUID SHARES / F&O ONLY** switch that filters both the table and the charts; F&O names are tagged. The table shows how long ago it broke, the delivery on the break, how far it fell under the average and where it is now; charts draw the 200-day average as a purple line. The replay is shown for both groups. Stocks outside F&O are not counted in the Today page's short ideas or in the confluence list (which needs futures open interest).

## Nifty trend flag
A banner on the Today page and at the top of Technical Patterns says where Nifty stands against its own 50 and 100-day averages (above both, below the 50, or below the 100), with the distances. When it is below the 50 or the 100, every fresh **breakout** on the Technical Patterns tab and on the Today charts carries a `NIFTY < 50DMA` or `NIFTY < 100DMA` mark (amber, then red) saying it counts for less. Breakdowns are not marked. It is a flag only: nothing is filtered or re-ranked by it. When the pattern replay is split by Nifty's state on the break day, daily breakouts show no real difference (about zero edge in all three states), while breakdowns did better against Nifty when the market was healthy (about 2.4% under it at 20 sessions, 64% right) than when it was already below its 50-day (they bounced).

## Sector clusters
When three or more stocks of the same kind of business are near a breakout (or just through one) at the same time, the page says so. **Sector** here is a hand-kept group in `config/sector_groups.csv` ("Life insurers", "Private banks", "Cement", about 470 stocks), finer than NSE's broad industries, in which "Financial Services" holds banks, insurers and brokers together; a stock with no group is never part of a cluster, and the file is meant to be edited. A candidate is a Breakout Base that is near its breakout or fresh, or an ascending triangle or rectangle that is a setup, at its top or freshly broken out. For each cluster the page shows the members, each with a small chart (the last 70 sessions: candles, 50, 100 and 200-day averages over delivered-share bars, blue where delivery is at least 1.25x its average, as on the Breakout Bases cards) and its delivery (today and over five sessions, each against the stock's own 20-session average) and one line on whether delivery is above normal, about normal or light across the group. It appears as a **Sector clusters** section on Today, below the three charts, the exchange and power activity and the short ideas (the five largest by size times delivery, each with charts for its strongest three members and the rest listed by name), above the Breakout Bases list (all of them, names and delivery only, since each stock has its own card below), as a tag on each near-breakout card, and as a flag on each member's own stock page.

## 52-week highs: copy table
The 52W Highs tab has a **Copy Table** sub-tab with two small plain tables, F&O names and non-F&O names, each sorted by the day's change and each with its own Copy Table button that puts the table on the clipboard tab-separated for pasting into a spreadsheet. ## 52-week highs: the close has to confirm
A stock counts as a fresh 52-week high only if its intraday high reaches the prior 252-session high **and** it closes above every close of that window. A new high that closes back under an earlier close is dropped. On the 20 Nov data this removed 5 of 22 names.

## NSE options tracker
The Exchange Tracker tab has a third exchange, **NSE**, with three views: **All NSE options** (equity plus commodity options, in the same layout as BSE and MCX, against Nifty), **Equity options** (index and single-stock options only, plus a monthly table of the index and stock split in rupees and contracts per day) and **Commodity options**.
- **Source and method.** NSE's own daily UDiFF bhavcopies: the F&O file (`/content/fo/`, index options IDO and stock options STO) and the commodity file (`/content/com/`, options on futures, from January 2024). Premium turnover is exact, as for BSE: an option row's transfer value is (strike + premium traded) x quantity, so subtracting strike x quantity leaves the premium. Equity quantity is contracts x the lot in the file; a commodity's contract multiplier (100 barrels for crude oil, 1,250 mmBtu for natural gas) is not in the file, so it is inferred from each day's own rows and snapped to the known contract sizes. The charts plot NSE's own share price (BSE: NSE, listed on 24 Sep 2026, read from BSE's equity bhavcopy since the NSE price file does not carry it), so the price line is short, as the share is new. Currency options are not included.
- **Commodity options.** The view shows daily premium turnover for the last 100 sessions with expiry days and the session before them colour-marked; monthly turnover split into expiry day, the day before and all other sessions, with the share on the first two; the cumulative turnover within each month for the last eight months, so the current month can be read against earlier ones; a table of each expiry (contracts and premium on the session before and on the day itself); and turnover by commodity. A commodity's expiry dates come from the option series it lists, and a session counts as the day before when a commodity expires on the next trading session.
- **NSE against MCX.** A small panel in the commodity view shows NSE commodity options as a share of NSE plus MCX option premium over a rolling three calendar months (equity options are not compared with MCX: they have no MCX counterpart) (a point needs a full window of both, so the lines start three months after MCX's history does and end where MCX's data ends: its site refuses connections from cloud servers, so it can lag).
- **Data.** Daily aggregates are kept in `data/nse_options_daily.csv`, `data/nse_commodity_daily.csv` and `data/nse_options_nofile.csv` (restored from the build cache) and seeded from `config/nse_options_seed.csv` and `config/nse_commodity_seed.csv`, so a build fetches only the sessions it does not have. Seeds cover January 2024 to 25 Nov 2026; `data/nse_share_price.csv` (seeded from `config/nse_share_seed.csv`) holds the NSE share's closes.

## Open interest on expiry days
A futures contract that expires on a session is settled at its close, but NSE's bhavcopy still lists it with the open interest it had going into the close. The desk used to add it to the day's total, so the expiry day read too high and the next session showed a drop that never happened (Blue Star: 51.9 lakh shares on 23 Nov, 38.8 lakh on 25 Nov, a "25% fall"; without the expiring series the 23 Nov close is 39.1 lakh and the change is 1%). `nse.fo_open_interest` now leaves out the contracts expiring on the session and counts what they carried in as leaving that day, so the real drop shows on the expiry day itself and the next session reads normally. `python oi_audit.py` re-checks every F&O stock and session in `data/raw/fo`: how many stocks each expiry affected and by how much, and a continuity check that a session's reported change equals the difference between its closing total and the previous close; the build prints a one-line version of that check for the latest session. Breaks it lists are mostly the sessions after a special weekend session (a Saturday budget session, Diwali Muhurat), which the desk's weekday sessions do not hold. Changing the parser invalidates the cached parsed days, so the first build after this re-downloads the history gradually (the backfill cap applies).

## Ranges: a stricter rectangle, as a trade
A **RANGES (NEW)** sub-tab in Technical Patterns sits beside the existing Rectangle sub-tab, which is unchanged (`ranges.py`, kept apart from `patterns.py`). A range needs: a boundary that breaks with at least three touches (the other side at least two), spaced a gap apart, each touch within 12% of the range's own height of the level (the old rule is a fixed 2% of price); touches that alternate between the two sides (at least three side changes); closes that cross the middle at least four times and stay inside; and no earlier excursion through a boundary. Each set-up is a trade plan: entry at the boundary, stop at the middle of the range, the measured-move target, how far the close is beyond the entry in R, and the prior trend (60 sessions before the range), so a break reads as continuing it or reversing it. The sub-tab has the daily and weekly scans, an F&O filter, a table and a chart for each set-up (touches numbered, entry, stop and target drawn).
`python range_replay.py` (run locally, about four minutes) replays every break as a trade for both this and the old rectangle scan at the same scan times: entered at the next session's open, stop at the middle of the range or its far side, leaving by a trailing exit (a close beyond the trailing 20-session low or high; 8 weeks on the weekly scan) or at the measured move. It reports win rate, average win and loss, expectancy and the share reaching 4R, in R (the distance from entry to the stop), and writes `config/range_replay.json`, which the sub-tab shows. On 1,901 past breaks the new ranges showed no sign of the asymmetry a low win rate needs.
